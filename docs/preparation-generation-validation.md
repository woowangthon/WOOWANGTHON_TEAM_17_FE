# 준비 → 생성 → 공동 캔버스 검증 기록

2026-11-11 현재 로컬 구현과 원형 진행 표시 후속 변경의 기록이다. 원격 PR 갱신·병합·서버 기동은 수행하지 않는다. 새 흐름과 검수 기준은 [기능 설명](preparation-schedule-design.md)과 [원형 진행 표시·경로 인계](generation-progress-handoff.md)를 따른다.

- FE: npm run check(타입·lint·빌드) 통과, npm test 135개 통과. Lint 오류 0, effect/ref/dependency 경고 10건. 원형 로딩 컴포넌트 정적 디자인 검사 0 FAIL/0 REFLEX/0 WARN. 브라우저 렌더 검사는 실행하지 않았다.
- BE: 인접 저장소의 pytest -m 'not mysql' 178개 통과, MySQL 172개 제외. in-process SQLite와 fake AI/router를 사용했다. Starlette/httpx·SQLite datetime adapter 경고가 남는다. 공용 DB는 관련 테이블 DDL만 읽기 전용으로 확인했으며 데이터 쓰기·초기화·migration은 실행하지 않았다.
- AI: 인접 패키지의 unittest 51개 통과. 실제 HTTPS 호출 없이 최초 분석의 근거·미예약 상태·오전/오후·상대 날짜·알 수 없는 항목을 검사했다.
- 검토: 별도 GPT-6.1 Sol high 계획, Luna high FE/BE 구현, root 통합 및 별도 Sol high 독립 검토. 오전/오후 시각, 미예약 숙소, 체크아웃만 알려진 경우, 숙소 범위 누락, 하루 8개 초과 약속 누락의 지적 5건을 수정하고 재검토에서 해소했다.

원형 게이지 후속은 FE만 변경했다. 위 BE·AI 수치는 이전 기능 커밋 849ca83/f2ce744의 검증 결과이며 이번 후속에서는 해당 소스를 바꾸지 않았다. 단계 기반 채움, 오류 시 미완료, 완료 프레임의 취소·늦은 응답 무시, 최초 엔진 준비, 미확인 PUT의 같은 키 재시도, 최신 편집 보존, 생성된 날짜 선택과 화면 상태 복원을 확인했다. 추가 독립 검토에서 발견한 연결선 삭제 ID 회귀, 같은 revision의 조회 오류 복구, 재진입 시 중복 화면 맞춤, 빈 날짜의 화면 복원 문제를 수정·재확인했다. 화면 복원은 viewport 준비를, 경로 맞춤은 노드 측정을 기다린다. 실제 UI 렌더 검수를 수행한 결과로 표현하지 않는다.

응답 유실 시 같은 키 재시도, 실제 완료 전 캔버스 이동 금지, 변경된 입력의 이전 결과 재사용 방지, OWNER 권한, 공동 편집 보존·CAS, 가져오기 중복·삭제 후 복구 방지와 메타데이터 위조/정상 undo를 확인했다. 숙소는 검증된 장소 집합을 바꾸지 않고 당일 마지막으로 배치하며, 퇴실일을 추가 숙박으로 만들지 않는다. 모르는 이동 시간·가격·체크인 시각을 만들어 넣지 않는다.

수동 검수는 파이참에서 인접 BE의 기존 run.py를 실행한 뒤 http://127.0.0.1:8017/ 에서 한다. 이 작업의 빌드가 FE dist에 준비되어 있으므로 별도 AI 서버는 필요 없다. 기본조건 저장 → 내 취향 분석·저장 → 모든 참여자 준비 완료 → 방장 일정 만들기 → 전체 로딩 → 같은 방 공동 캔버스 순서로 확인한다. 개인 원문·개인 일정은 본인 화면에만 표시되는지 두 기기로 확인한다.

실제 Gemini/Kakao 응답·MySQL 쓰기/경합·모바일/키보드 렌더·두 기기 실사용 검수는 수행하지 않았다. 이 미실행 항목을 실제 통합 검증 완료로 표현하지 않는다. PR 제목·본문은 사용자 검수 후 갱신한다.

## 2026-11-12 기간 확대 후 캔버스 배치

2일에서 3일로 재생성하는 회귀 시나리오를 추가했다. 기존 출처가 있는 자동 경로와 관련 선은 교체되고, 직접 바꿔 출처가 없는 장소·댓글·대안과 남은 연결은 보존된다. 현재 생성 버전은 날짜별 1·2·5곳을 포함하며 모든 일정 시각이 새 버전에서 온다는 것을 검사한다. 같은 결과 재호출은 중복 추가나 삭제 카드 복원을 하지 않는다. 날짜 연결은 기존 자동 날짜의 순차 연결이 온전할 때 새 날짜까지 확장하고, 빈 목록·끊긴 연결·사용자 순서를 유지한다.

새 날짜의 생성 카드가 세 곳을 넘으면 간격 보정이 적용되지 않던 문제를 수정했다. 네 곳·다섯 곳·여섯 곳과 가변 측정 크기의 카드로 겹침·경계·방문 순서·첫 편집 좌표를 검사했다. FE `npm test` 181개, `npm run check`의 타입·lint·빌드가 통과했다. 기존 lint 경고는 남는다. BE non-MySQL 203개 통과, MySQL 177개 제외. Starlette·SQLite 관련 deprecation 경고가 남는다.

모든 요청을 가로채는 정적 테스트 화면에서 1440×900·390×900의 3·4·5곳 날짜 프레임을 확인했다. 12개 카드의 겹침 0건, 그룹 경계 내 표시, 전체 보기·재진입과 PC 첫 드래그 후 나머지 카드 위치 및 source/schedule 유지가 통과했다. 실제 서버·유료 AI·경로 제공자·공용 DB 쓰기를 수행한 검사는 아니다. 실제 방 상태는 읽기 전용으로만 확인했다.

별도 GPT-6.1 Sol high 계획 → Luna high FE·BE 구현 → root 통합·검사 → 별도 GPT-6.1 Sol high 독립 검토 순서로 진행했다. 독립 검토에서 조치할 finding은 없었다. 별도 역할 호출 대신 같은 역할 지침과 모델·추론 수준을 명시한 하위 에이전트를 사용했다. 사용자가 기존 `run.py`를 재실행하고 새로고침해 검수한다. 이미 저장한 날짜 연결을 재호출로 복원하지 않으므로 누락된 기존 연결은 캔버스에서 직접 잇는다. 변경은 로컬 전달 범위이며 원격 PR은 사용자 제목·본문 검수 후 갱신한다.

## 2026-11-12 기간·날짜 변경 시 전체 교체

사용자 후속 요구로 새 생성 버전의 수동 편집 보존 규칙을 전체 교체로 바꿨다. 위 기간 확대 기록은 이전 동작의 검증 이력이다. 현재 규칙은 [여행 준비 흐름](preparation-schedule-design.md)과 [공동 캔버스](canvas-studio.md)를 따른다. 새 버전을 처음 가져오는 성공 시점에 날짜·장소·댓글·대안·사용자 날짜·연결·배치를 새 계획만으로 만들고, 같은 버전 재열기는 수정·삭제 상태를 유지한다. 실패·stale·CAS 충돌은 기존 초안을 유지한다.

PUT의 필수 `expectedSourcePlan`을 현재 source 컬럼과 비교해 이전 탭의 문서 저장을 거부한다. FE도 더 높은 revision의 새 source를 먼저 반영하고 이전 pending·충돌·history를 정리한다. 별도 검토에서 확인한 409 조회 후 새 source에 이전 댓글이 합쳐지는 문제, 진행 중 PUT 및 결과 미확인 재시도에 묶인 인계가 끝나지 않는 문제, 이전 인계가 새 일정의 무관한 저장을 기다리는 문제를 수정하고 회귀 검사를 추가했다. 단순 PLACE 교체의 source/schedule 제거와 같은 source의 정상 undo도 재검증했다.

FE `npm test` 190개와 `npm run check`의 타입·lint·빌드 통과. lint 오류는 없고 hook/ref·memoization 등의 경고가 남는다. BE non-MySQL 207개 통과, MySQL 177개 제외. 독립 Sol high 검토의 focused API·동기화·엔진·인계 56개도 통과했고 지적 사항은 수정 후 해소했다. Sol high 계획, Luna high BE·동기화·UI 구현, root 통합과 Sol high 독립 검토를 명시적 모델 실행으로 수행했다.

모든 요청을 가로챈 1440×900·390×900 화면에서 3일→2일→3일→13~14일로 연속 변경했다. 이전 수동 장소·댓글·날짜·메뉴·이력이 사라지고 최신 카드와 연결만 남는 것, 13일이 1일차로 표시되는 것, 같은 버전 화면 전환에서 댓글 초안 유지, 새 source에서 초안 제거, 이전 추천 요청의 늦은 결과 무시와 재진입을 확인했다. 실제 생성기·Kakao·MySQL 쓰기·두 기기 실서버 검수는 이 검사에 포함하지 않는다. 공용 방은 읽기 전용으로만 진단했다.

API 계약의 기존 일정 생성·공동 캔버스 페이지에 전체 교체 및 source 확인 규칙을 반영했다. 새 DB migration은 없다. 사용자는 PyCharm에서 기존 `run.py`를 재실행하고 브라우저를 새로고침한 뒤 날짜나 조건을 바꿔 새 생성으로 검수한다. 이미 가져온 같은 결과를 다시 여는 것은 여전히 편집 보존 동작이다. 원격 push·PR은 제목·본문 검수 후 진행한다.
