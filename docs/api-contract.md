# API 계약 운영

## 공용 원본과 연결

Notion 공통자료의 [API 계약](https://app.notion.com/p/40ee977e49088030a073ffd13d06c144)과 그 기능별 하위 페이지가 FE·BE 공용 명세 원본이다. FE가 API 규격 작성 책임자이고 BE는 그 명세를 읽고 구현·검증한다. 이 문서는 운영 절차이며 endpoint의 별도 원본이 아니다. 팀 참여·작업 안내는 [공통 가이드](https://app.notion.com/p/40ee977e4908813e9226ce66a9be8cf2)를 참고한다.

각 팀원은 자기 계정으로 Notion 플러그인을 연결하고 페이지 읽기·필요한 쓰기 권한을 확인한다. clone은 계정 인증이나 권한을 공유하지 않는다.

## 페이지 구조와 갱신 위치

- **메인 목차**: 기능명·상태·기능 페이지 링크·FE/BE PR만 관리한다. API 상세와 예시를 본문에 계속 추가하지 않는다.
- **[공통 규칙](https://app.notion.com/p/40ee977e49088189b512e6e817984d48)**: 공통 인증·오류 형식·중복 요청 처리·작성 양식을 한 번만 정의한다. 기능 페이지는 적용 여부와 예외만 적는다.
- **기능별 하위 페이지**: 작업 시 메인에서 기존 기능 페이지를 먼저 찾는다. 없을 때만 기능 단위로 만들며 같은 기능의 후속 작업은 기존 페이지를 갱신한다. 커밋·PR마다 새 페이지를 만들지 않는다. 현재 시작 기능은 [여행방 시작](https://app.notion.com/p/40ee977e49088105a9b4ce4df0aef6f8)이다.
- 기능 페이지에는 목적·상태·method/path·요청/응답·권한·주요 오류·필요한 특이사항·FE/BE PR·실제 검증 결과를 간결하게 적는다. 긴 DB 의존성·검증 기준은 필요한 경우 접기 영역으로 분리하며 공통 설명을 반복하지 않는다.
- FE root가 기능 페이지의 규격 본문과 메인 링크를 작성한다. BE는 기능 페이지의 구현 상태·BE PR·검증 결과와 메인 해당 행만 갱신한다. 상태·PR은 두 위치를 맞추고, 일부 API만 완료됐으면 메인은 작성 중 또는 구현 요청으로 유지하며 완료 범위를 기능 페이지에 표시한다.
- 이동·개편 시 계약 내용을 먼저 하위 페이지에 보존하고 관련 링크를 갱신한 뒤 메인을 정리한다. 다른 기능·하위 페이지를 삭제하거나 같은 명세를 여러 곳에 복제하지 않는다.

## 기능 요청부터 연동까지

1. FE root가 Notion 메인 목차에서 해당 기능 페이지를 찾고 공통 규칙과 함께 읽어 기존 API를 재사용한다. 없거나 부족하면 기능 요청 범위에서 method/path, 요청·응답 필드와 예시, 인증·권한, 오류를 정해 명세를 작성·보완한다. 불명확한 요구사항은 필요한 부분만 확인한다.
2. 정리 중에는 `작성 중`, BE가 구현할 수 있도록 규격을 정리했으면 `구현 요청`으로 표시한다. FE가 정리한 `구현 요청` 명세가 BE 구현 기준이다. 별도 FE·BE 이중 승인이나 필수 API ID·개정·승인자 필드를 요구하지 않는다.
3. FE는 BE가 준비될 때까지 같은 규격의 mock으로 화면과 상태 처리를 개발한다. mock과 실제 서버 연결을 명확히 구분한다.
4. BE는 명세를 읽고 구현·검증한다. 부족·모순·구현 불가능한 부분이나 보안상 문제만 구체적으로 FE에 확인하며 규격을 임의 변경하지 않는다. BE는 명세 본문을 수정하지 않고 구현상태와 관련 BE PR 링크만 갱신한다. 구현·검증을 마치면 `구현 완료`로 표시하고 실제 테스트 방법을 남긴다.
5. FE는 BE 구현·검증 결과와 실행 가능한 환경을 확인한 뒤 실제 연동을 검증한다. PR 존재나 `구현 완료` 표시만으로 배포·연동 성공을 가정하지 않는다.

## 작성 책임과 변경 대응

- FE root가 Notion 조회·명세 쓰기·적용 기준 판단을 맡고 하위 에이전트에는 관련 명세 내용과 상태를 전달한다. 하위 에이전트는 필요한 변경을 root에 보고한다. FE 담당이 겹치면 API별 작성자를 정한다.
- 기능 요청에 필요한 Notion 작성·상태·PR 링크 갱신은 기본 작업 범위다. 명시적 읽기 전용·로컬 전용 지시가 있으면 외부 쓰기를 하지 않는다.
- 명세 수정 전 최신 내용을 읽고 대상 항목만 수정한다. 기존 실제 동작을 깨는 변경은 FE가 영향을 확인한 뒤 명세를 수정하고 변경 내용을 공유한다. 작업 중 의미 있는 명세 변경을 확인하면 차이를 비교하고 영향받는 부분만 수정·재검증한다. 고정된 횟수의 재확인 절차는 두지 않는다.
- 조회 실패나 본문 누락을 API 부재로 단정하지 않는다. 쓰기 실패를 성공으로 보고하지 않으며, 결과가 불확실하면 재시도 전에 조회해 중복 API·페이지 생성을 피한다. 실패 시 로컬 초안과 독립 작업은 계속하되 확인하지 못한 명세나 연동을 완료로 보고하지 않는다.

## PR 기록

FE·BE는 각 레포에서 별도 이슈·브랜치·커밋·PR을 사용하고 서로 링크한다. 양쪽 PR에는 해당 기능 하위 페이지와 적용한 공통 규칙 링크, 사용한 method/path·내용 요약, 실제 검증 결과와 남은 사항을 기록한다. Notion URL은 가변이므로 필요하면 관련 본문을 PR이나 문서에 인용하되 별도 스냅샷 파일·버전 관리 체계를 요구하지 않는다.

계약 승인 여부만으로 Draft를 강제하지 않는다. 기존 Git workflow의 필수 검사·리뷰·미해결 사항 기준으로 Ready 여부를 판단하고, mock 검증을 실제 연동 검증으로 표현하지 않는다. 사람만 병합한다. OpenAPI 생성만으로 실제 권한·오류 동작이 검증된 것은 아니다. Notion↔Git 자동 동기화·watcher·FE 타입 자동 갱신은 이 절차에 포함하지 않는다.

## 기능별 확인 대상

아래 목록은 기능별 명세 작성 시 확인할 주제이며 실제 API 정의가 아니다. 작업 시 Notion의 현재 항목을 확인한다.

- 방 생성·참여·재접속과 참여 식별 방식.
- 공통 조건·개인 원문·해석·확정 데이터 형식.
- 생성 가능 상태와 실패·재시도 방식.
- 일정·장소·이동·비용·정보 출처 형식.
- 수정 초안·검사·적용·동시 저장 충돌·복원 계약.
- 개인별 조회·수정 권한과 공통 오류 응답.

## 시작 페이지 · 기기 세션과 여행 진입

후속 [여행 준비·개인 조건](https://app.notion.com/p/412e977e49088197b345d73603c6a27f)은 구현 요청 상태다. 준비 정보·공통 조건·본인 초안·AI 제안·직접 확정의 6개 API와 버전/권한/개인정보 규칙을 해당 페이지에 정의했다. 현재 FE의 두 화면은 메모리 UI 초안이며 신규 API는 아직 연결하지 않는다. BE 실행 요청은 [백엔드 인계](backend-handoff.md)를 따른다. 기존 시작 API의 규격·DTO는 유지한다.

- BE의 5개 API 구현과 격리 MySQL 검증은 [BE PR #9](https://github.com/woowangthon/WOOWANGTHON_TEAM_17_BE/pull/9)에 기록돼 있다. 현재 FE는 그중 세션·생성·참여·재접속을 연결한다. 전체 계약 상태와 실제 검증 범위는 [여행방 시작](https://app.notion.com/p/40ee977e49088105a9b4ce4df0aef6f8) 및 [공통 규칙](https://app.notion.com/p/40ee977e49088189b512e6e817984d48)을 따른다.
- 범위: 기기 세션을 확보하고 여행을 생성하거나 기존 여행에 참여하며, 기기의 여행 목록을 다시 조회하고 참여를 재연결한다.
- 명세 endpoint 목록: `POST /api/v1/device-session`, `POST /api/v1/trips`, `POST /api/v1/trip-memberships`, `GET /api/v1/device-session/trips`, `POST /api/v1/trips/{tripId}/reconnect`. 요청·응답 필드, 상태코드, 공통 오류는 원본 Notion 명세를 따른다. 이 운영 문서는 상세 DTO를 복제하지 않는다.
- 본인 식별: HttpOnly device-session cookie를 사용한다. 브라우저 JavaScript가 쿠키 값을 읽거나 개인 식별자를 직접 저장하지 않는다. 기기 내 여행 목록과 재연결은 해당 세션에 귀속한다.
- 중복 제출: 여행 생성 및 참여 요청은 `Idempotency-Key`를 전송하고 BE는 키를 24시간 보관해 같은 요청의 중복 저장을 막는다. 이를 위해 BE의 영속 device-session, membership mapping 및 idempotency 저장소가 필요하다. 정확한 key 형식과 동시 중복 응답은 원본 명세를 따른다.
- 입력 정규화: 여행 이름과 닉네임은 trim 후 Unicode code point 수를 세며, 이름은 40자, 닉네임은 20자 이내다. 제어문자 U+0000–U+001F 및 U+007F–U+009F 및 줄 구분자 U+2028/U+2029를 거부한다. 초대 코드는 trim 후 ASCII 대문자로 정규화하고 `^[A-Z0-9-]{1,20}$`를 만족해야 한다.
- 코드: 실제 생성 코드는 `CB-` 접두어와 무작위 10자리 값으로 구성된다. `CB-DEMO`는 UI fixture 전용 예외이며 서버 초대 코드 형식이나 실제 참여 가능 코드가 아니다.
- FE 상태: 기본 시작 페이지와 `/room.html`은 실제 HTTP·기기 쿠키 기반이다. 이전 `src/features/entry/mockRequests.ts`는 보존된 fixture이며 기본 페이지에서 호출하지 않는다. 최근 목록 API는 제공되지만 이번 UI에서는 사용하지 않는다. 입력·잠금·재시도 검사와 실제 브라우저 연동 검증 결과는 PR에 구분해 기록한다.
